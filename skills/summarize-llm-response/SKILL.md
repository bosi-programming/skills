## First, check this applies

A blanket rule ("run this before any communication") will hand you work this skill has nothing to say about. Read the request and stop here if it is any of:

- A yes/no answer or a single-line fact.
- Code, config, or a diff, with no prose around it.
- A clarifying question back to the user.
- A git commit message or PR description.
- Something the user asked for at length, in detail, or in narrative form.

Stop means stop: answer normally, apply nothing below, and say nothing about having skipped it.

## Attribution

Linear, Todoist and Notion posts must include `[Text Generated by AI - {model_id}]` (use short model ID, e.g., `claude-opus-4-6`).

Slack messages and in-conversation replies carry no tag.

Placement:
- **Linear/Notion**: first line of the body. Title field is separate — no tag there.
- **Todoist tasks**: first line of the description field. Title field is separate.
- **Comments (all tools)**: first line of the comment.

### Edge cases

- **Editing human-written content**: do NOT prepend the tag. Add `[Section updated by AI - {model_id}]` before the edited section only.
- **Replies on existing threads**: always include the tag as first line of the reply.
- **Updating a tagged post**: do not duplicate the tag. If a different model edits the post, keep the original tag and append `[Updated by AI - {model_id}]` below it.
- **Mixed content**: tag only the portion you wrote, not the entire post.
- **Same model re-editing its own post**: keep the original tag unchanged.

## Line budget

- A line/sentence must have between 1 to 20 words.

One idea per line. Cut every word that carries none. Past the cap, split the line or cut it. Do not pad a short line to look complete.

Tighter caps stated elsewhere still win: 8 words for a Todoist title, 10 for a Linear issue title, 20 for a TL;DR.

## Drafting when you cannot post

No integration for the destination? Output the content only — exactly what would be submitted, field by field. No preamble, no "here's what I'd post", no commentary after. A wrapper leaks the wrong markup into Slack drafts and buries the attribution tag.

## Format Rules

### For user-facing summaries (in-conversation)

No attribution tag for in-conversation responses.

- **TL;DR last** (when 3+ findings): 1 sentence, max 20 words. Omit for 1-2 finding summaries — the findings speak for themselves.
- **Findings**: bullet list, one line each. No filler words.
- **Evidence**: inline refs (file:line, log ID, ticket ID). No separate "references" section.
- **Next steps**: numbered, actionable, 1 line each. Omit if none.
- Max 15 bullets. If over, keep highest-severity and append: "*N lower-priority items omitted — ask to expand.*"

### For Linear posts (issues, comments)

- **Title** (issues only): `[Category] Concise description` — max 10 words. Category is free-form, match issue type (Bug, Feature, Chore, Spike). Use team conventions when known.
- **Body**:
  - 1-sentence summary.
  - Bullet list of details/findings (max 10 bullets).
  - Action items as checklist (`- [ ] item`).
- No greetings, sign-offs, or filler.
- Use markdown formatting: bold for emphasis, code blocks for IDs/errors.

### For Todoist posts (tasks, comments)

- **Task title**: verb-first, max 8 words. (e.g., "Fix null check in payment flow")
- **Description**: 1-3 bullet points of context. Omit if task title is self-explanatory.
  - If description is omitted, skip the attribution tag — title-only tasks have no field for it.
- **Comments**: max 3 sentences. Link to sources instead of quoting.

### For Notion posts (pages, comments)

- **Page title**: concise, no redundant prefixes like "Notes on" or "Summary of".
- **Body**:
  - Lead with 1-sentence summary or TL;DR.
  - Use headings only when content exceeds 5 bullets.
  - Bullet lists over paragraphs. One idea per bullet.
  - Action items as checklist (`- [ ] item`).
- **Comments**: max 3 sentences. Reference specific content, don't restate it.

### For Slack messages

No attribution tag for Slack.

Slack uses mrkdwn, not markdown: `*text*` = bold, `_text_` = italic. Do NOT use `**text**` — it renders as literal asterisks in Slack.

- **Lead with the key fact or action**: what's happening, when, who's affected. Max 1 sentence.
- **Use bold section headers** (`*Header:*`) for distinct sections (What, When, Impact, Action needed).
- **Bullet key details** under headers. Max 3-4 bullets per section.
- No TL;DR header — Slack messages are scanned, not read top-to-bottom.
- Use emoji sparingly for visual anchoring (`:warning:`, `:white_check_mark:`) — only when it aids scanning.
- No filler openers ("Hey team!", "Hope you're all well").
- End with a clear next action or "No action needed" if informational.

### For markdown files (technical/operational docs only)

Applies to: READMEs, ADRs, runbooks, changelogs, investigation notes.
Does NOT apply to: blog posts, literary content, or files where user specifies narrative style.
Does NOT override format rules from `tech-text-review`, `ai-md-review`, or `literatura-review` skills — those take precedence for their respective file types.

- Prefer bullet lists over prose.
- One idea per line/bullet.
- Headings: short, no articles ("Setup" not "The Setup Process").
- No filler intro/outro paragraphs.
- Tables over repeated bullet structures when comparing 3+ items.
- Code blocks with language tags for any code/config/commands.

### Empty results

- State the null result in 1 line: "No matching logs for service X between {start} and {end}."
- Include what was searched and the scope/timeframe.
- Suggest next step if obvious (broaden time range, check different service, etc.).
- Do not pad with filler or apologize.

## Anti-patterns

- "Here's a summary of what I found..." — just give the summary.
- "I hope this helps!" — never.
- Repeating the user's question back.
- Filler-lead bullets: "The issue is that..." or "This is because..." — lead with the fact.
- Paragraphs where bullets suffice.
- Wrapping a single sentence in a heading + paragraph when a bullet would do.
- Applying TL;DR header format to Slack messages — use bold section headers instead.

## PII & Sensitive Data

- Never include raw customer emails, phone numbers, or IPs in external posts.
- Mask PII: emails → `u***@***.com`, IPs → `x.x.x.x`, phones → `[PHONE]`.
- Use internal IDs (`user_id: abc123`) instead of personal identifiers.
- Customer names → `[CUSTOMER]` in Linear/Todoist/Notion posts. Keep real identifiers only in source tickets.
- Never post secrets, API keys, or credentials. Replace with `[REDACTED]`.

## Audience Adaptation

- Default audience: internal engineers. Use technical refs (file:line, error codes, trace IDs).
- Non-technical audience (stakeholder updates, customer-facing Notion pages): replace file:line refs with plain descriptions, drop code blocks, use business-impact language.
- When audience is ambiguous, ask before posting.

## Examples

### Good user summary (in-conversation — no attribution)

> - `PaymentService.ts:142` — `webhook.metadata` can be null for v2 partners
> - Error rate: 12/hr since deploy `abc123` (2h ago)
> - Only affects partners with `apiVersion: "v2"` flag
>
> 1. Add null check at `PaymentService.ts:142`
> 2. Backfill failed webhooks via retry queue

> **TL;DR**: Payment webhook fails for partners using v2 API due to missing null check.

### Good Linear issue

> **Title**: [Feature] Add retry logic for failed partner callbacks
>
> [Text Generated by AI - claude-opus-4-6]
>
> Partners on legacy tier miss ~8% of event callbacks due to timeouts. No retry mechanism; events dropped silently.
>
> - Affects 23 partners, ~400 events/day
>
> - [ ] Implement exponential backoff retry (max 3 attempts)
> - [ ] Add dead-letter queue for permanently failed events
> - [ ] Notify partner via email after 3 failures

### Good Linear comment

> [Text Generated by AI - claude-opus-4-6]
>
> Confirmed this only affects v2 partners. Retry queue backfill completed — 847 events reprocessed, 3 permanently failed (invalid payload).
>
> - [ ] Monitor error rate for 24h
> - [ ] Close ticket if no recurrence

> :warning: *Hotfix deploy tonight at 10pm EST — 2-min maintenance window.*
>
> *What's changing:* Null check added at `PaymentService.ts:142` — fixes webhook failures for v2 API partners.
>
> *Impact:* v2 API partners unaffected after deploy. No action needed.
